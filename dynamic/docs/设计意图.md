# 动态评测参数归属设计意图

## 核心原则

动态评测的 `run_eval.py` **只定义三类参数**：

1. **模式选择与数据集参数** - `--dataset`、`--sample`、`--questions`（指定 dataset 进入 replay 模式，否则 generate 模式）
2. **评测器与场景生成参数** - `--evaluator-config`、`--user-simulator-config`、`--scenario-model`/`--scenario-base-url`/`--scenario-api-key`、`--num-memories`/`--num-queries` 等 generate 模式参数
3. **评测基础设施参数** - `--out-dir`（dynamic 自行声明，不调用 `add_eval_args()`）

所有其他参数（LLM 凭据、记忆后端连接、commit 超时、插件特有配置）
**完全委托给插件和记忆后端定义**，不由 dynamic `run_eval` 直接声明。

> 设计原则与 benchmark 评测一致，详见 `benchmarks/doc/设计意图.md`。

## 插件无关化设计

dynamic `run_eval.py` 支持不同插件评测，核心是 **参数声明、参数校验、插件加载、插件使用**
四个环节全部插件无关：

### 参数声明：预解析 + 委托

`add_agent_plugin_args(parser)` 在 `shared/eval_base.py` 中实现：

1. 预解析 `sys.argv` 找到 `--agent-plugin` 的值（默认 `echo_agent`）
2. 通过 `plugins.get_plugin_class(plugin_name)` 获取插件类
3. 调用 `plugin_cls.add_arguments(parser)` - 插件在此时声明自己需要的所有参数

`run_eval.py` 不引用任何插件特有参数名（如 `--echoagent-url`、`--username`、`--password`）。
切换插件只需 `--agent-plugin bare_llm`，对应插件的参数自动出现在 `--help` 中。

### 参数校验：三层分工

| 层级 | 校验函数 | 校验内容 | 定义位置 |
|------|---------|---------|---------|
| 通用 | `validate_eval_config(config)` | LLM 凭据、并发数、超时、top_k 等 `EvalConfig` 字段 | `shared/eval_base.py` |
| dynamic 自有 | `validate_dynamic_args(args)` | evaluator_config 文件、dataset 文件、scenario_* 参数、num_* 数值范围 | `dynamic/run_eval.py` |
| 插件特有 | 插件 `setup(config)` | 插件特有参数（如 echo_agent 的 URL/凭据，通过 login 失败暴露） | `plugins/*/plugin.py` |

`validate_dynamic_args` **不校验**任何插件特有参数或通用 LLM/后端参数。
插件特有参数的校验由插件 `setup()` 自然承担--如果参数缺失或错误，`setup()` 中的
初始化逻辑（如 HTTP 登录）会抛出异常，`run_eval.py` 捕获后退出并提示。

### 插件加载：flat dict 传递

```python
agent_config = {**vars(args), "benchmark_name": "dynamic", "run_id": run.result_dir.name}
agent_plugin = load_agent_plugin(args.agent_plugin, agent_config)
```

所有 CLI 参数以 flat dict 传入插件的 `setup(config)`。每个插件用 `config.get(key, default)`
读取自己关心的字段，忽略不相关的字段。`benchmark_name` 和 `run_id` 用于记忆后端
identity isolation（`provision_isolated_identity`）。

### 插件使用：仅调用 AgentPlugin 接口

dynamic `run_eval.py` 和 `workflows.py` 只调用 `AgentPlugin` 接口方法：

| 接口方法 | 用途 | 调用位置 |
|---------|------|---------|
| `inject_memories(memories)` | 注入背景记忆到记忆后端 | `workflows.py` |
| `create_session(title)` | 创建 QA 会话 | `workflows.py` |
| `simulate_typing(...)` | 打字模拟触发 prefill（如插件支持） | `workflows.py` |
| `send_message(session, msg)` | 发送消息并接收回复 | `workflows.py` |
| `memory_client.health()` | 健康检查（评测启动时无条件调用） | `run_eval.py` |
| `getlog()` | 收集后端日志（echomem 按本运行租户/user 拉取 `GET /api/logs`：注入记忆全部日志 + 本次 QA 日志） | `run_eval.py` |
| `teardown()` | 释放资源 | `run_eval.py` |

`workflows.py` 中的结果 metadata 使用 `args.agent_plugin`（插件名）记录，不引用
任何插件特有字段（如 `echoagent_url`）。

### recalled memories 收集机制

每轮 QA 的 `relevant_memory`（召回的记忆列表）通过 `_ask_agent`（`workflows.py`）
收集，有两个来源，优先级递减：

1. **typing simulation 路径**：若插件支持 `simulate_typing`（仅 `echo_agent`），
   从 `TypingResult.memory_items` 获取 prefill 阶段召回的记忆。
2. **`send_message` 回退路径**：若 typing simulation 未产生 `memory_items`，
   从 `AgentResponse.memory_items` 获取--这是 `send_message` 返回的检索结果，
   适用于所有不支持 typing simulation 的插件（`vikingbot`、`echomem_mcp`、
   `openviking_mcp`、`bare_llm`）。

```python
# _ask_agent 中的收集逻辑
if not memory_items:
    memory_items = response.memory_items or []
```

收集到的 `memory_items` 与 `AgentResponse` 一起传入
`collect_round_metrics(round_data, response, memory_items)`，序列化为
`relevant_memory` 字段保存在每轮结果中。

### 指标采集统一

`collect_round_metrics(round_data, response, memory_items)` 从 `AgentResponse`
标准字段与 `extra` 直接读取全部指标，不再经 `done_event` dict 中转：

- **标准字段**：`ttft_ms`（四舍五入到 0.1ms）、`prompt_tokens`、
  `completion_tokens`、`cached_tokens`、`prefetch_committed`
- **`extra` 字段**：`elapsed_s`、`retrieval_latency_s`、`llm_latency_s`、
  `tool_call_count`（默认 0）、`iterations`（默认 1）——由插件从 SSE done
  事件的 `metrics`（ms→s 换算）填充
- **`round_data` 元数据**：`is_new_session`、`is_injection`、`complexity`、
  `ground_facts`、`query`/`query_length`
- **`memory_items` 参数**优先于 `response.memory_items`，序列化为
  `relevant_memory`

失败轮（`_failed_round`）返回与 `collect_round_metrics` 对齐的 schema：
`completion_tokens=0`、`elapsed_s`/`retrieval_latency_s`/`llm_latency_s=None`、
`tool_call_count=0`、`iterations=1`。`compute_summary` 基于这些字段聚合
`avg_elapsed_s`/`avg_retrieval_latency_s`/`avg_llm_latency_s`/
`avg_completion_tokens`/`avg_tool_call_count`/`avg_iterations`。

## 与 benchmark 评测的差异

| 方面 | benchmark | dynamic |
|------|-----------|---------|
| 默认插件 | `bare_llm` | `echo_agent` |
| QA 参数 | 插件通过 `add_qa_args()` 声明 | `echo_agent` 不声明 QA 参数（走 EchoAgent 管线）；`bare_llm` 声明 |
| 场景生成 | 无 | `--scenario-*` 三参数 + `--num-memories`/`--num-queries` 等 |
| Judge 参数 | `--judge-model` 等 | 无独立 Judge；质量评估用 `--llm-*` 参数 |
| 评测器配置 | 无 | `--evaluator-config` YAML（维度 + prompt 模板）|
| 并发 QA | `--concurrency` 实际生效（`ThreadPoolExecutor` 并行） | 不支持并发，不声明 `--concurrency`（见下文） |

## 串行执行约束

dynamic 评测**不支持并发 QA**，所有查询必须串行执行。`run_eval.py` 不声明
`--concurrency`（也不调用共享的 `add_eval_args()`），直接声明 `--out-dir`
一个基础设施参数。评测启动时无条件执行 `agent_plugin.memory_client.health()`
健康检查，通过后才进入正式评测流程。

两种模式均为串行的原因：

- **generate 模式**：`evaluator.generate_next_query()` 接收 `previous_queries` 和
  `previous_replies` 作为上下文（`workflows.py:143`）。第 N+1 轮查询的生成依赖第 N
  轮的回复，无法提前生成。`for round_index in range(args.num_queries)` 串行循环
  （`workflows.py:142`），每轮结束后将 query 和 reply 追加到上下文列表
  （`workflows.py:179-180`）。

- **replay 模式**：每个 sample 的查询发送到同一 `qa_session`（`workflows.py:264`），
  会话内上下文随每轮查询累积。后续查询的回复受前序查询及回复影响，无法并行。
  外层 `for plan in plans` 和内层 `for job in jobs` 均为串行 `for` 循环。

与 benchmark 的差异：benchmark 的每个 QA 任务独立（无会话上下文累积），可以用
`ThreadPoolExecutor` 并行处理多个任务（`benchmarks/locomo/qa.py:200`）。dynamic
的查询间存在上下文依赖，无法并行。

## 查询生成的上下文依赖机制

dynamic 评测的 generate 模式在每次生成新用户查询时，**携带完整的历史上下文**。
这是 dynamic 模式的核心设计：模拟真实用户的多轮对话行为，每轮查询都基于之前
的对话历史和背景记忆。

### 上下文数据来源

`workflows.py` 的 `run_generate_mode` 串行循环 `for round_index in range(args.num_queries)`，
每轮调用 `evaluator.generate_next_query(context)` 时传入以下上下文字典：

```python
generated = evaluator.generate_next_query({
    "round_index": round_index,           # 当前轮次（从 0 开始）
    "previous_queries": previous_queries,  # 前 N 轮的全部查询文本
    "previous_replies": previous_replies,  # 前 N 轮的全部回复文本
    "is_new_session": not session_id,      # 当前是否为新会话首条
})
```

每轮结束后，当前查询和回复被追加到上下文列表（`workflows.py:183-184`）：

```python
previous_queries.append(query)
previous_replies.append(str(metrics.get("reply") or ""))
```

因此第 N+1 轮的查询生成能看到前 N 轮的**全部问答对**（受下方字符上限约束）。
第 1 轮（`round_index=0`）的 `previous_queries` 和 `previous_replies` 为空列表。

### 上下文构造过程（`simulator.py: _generate_dynamic_query`）

`_generate_dynamic_query` 将上下文字典转换为 LLM prompt 的 4 个填充变量：

| 填充变量 | 来源 | 构造方式 |
|---------|------|---------|
| `{background_facts}` | `self.background_memories[:10]` | 取前 10 条背景记忆，格式 `- [f1] 文本...`，每条一行 |
| `{conversation_history}` | `previous_queries` + `previous_replies` | 从最近轮次往回累加，格式 `User: xxx\nAssistant: xxx`，直至 256K 字符上限 |
| `{round_index}` | `context["round_index"]` | 当前轮次号（+1 后从 1 开始） |
| `{is_new_session}` | `context["is_new_session"]` | 布尔值的字符串形式（`True`/`False`） |

#### 对话历史累加算法

```python
_MAX_HISTORY_CHARS = 256_000  # ≈64K tokens at ~4 chars/token
history_parts = []
total_chars = 0
for i in range(len(previous_queries) - 1, -1, -1):  # 从最近往回
    q = previous_queries[i]
    r = previous_replies[i] if i < len(previous_replies) else ""
    entry = f"User: {q}\nAssistant: {r}"
    if total_chars + len(entry) > _MAX_HISTORY_CHARS:
        break                    # 超出上限，丢弃更早的历史
    history_parts.append(entry)
    total_chars += len(entry)
history_parts.reverse()          # 恢复时间正序
history_text = "\n".join(history_parts) if history_parts else "(No previous conversation)"
```

- **从最近往回累加**：优先保留最近的对话，较早的历史在超出 256K 字符时被截断。
- **256K 字符上限**：约 64K tokens（按 ~4 chars/token 估算），防止 prompt 超出
  LLM 上下文窗口。
- **无历史时**：第 1 轮或会话重置后，显示 `(No previous conversation)`。

#### 背景记忆

`background_facts` 取自 `self.background_memories`（注入前由
`generate_background_memories()` 生成），截取前 10 条。这些记忆同时通过
`inject_memories()` 写入记忆后端，是评测的「地面真相」--查询通过 `ground_facts`
字段引用记忆 ID，评估时据此判断回复是否正确回忆了对应事实。

### persona_prompt 模板

4 个填充变量通过 Python `str.format()` 注入 `user_simulator_config` 的
`persona_prompt` 模板。模板在 `__init__` 中校验，必须包含全部 4 个占位符
（`simulator.py:70-76`）：

```python
required_placeholders = [
    "{background_facts}", "{conversation_history}",
    "{round_index}", "{is_new_session}",
]
```

默认模板位于 `configs/user_simulator_default.yaml`，结构为：

1. **场景设定**：模拟一名后端工程师与 AI 助手讨论微服务项目
2. **角色指令**：要求生成引用历史讨论的查询，不直接引用记忆原文
3. **Current Context**：4 个占位符填充区域
   - `### Background Facts` ← `{background_facts}`
   - `### Conversation History` ← `{conversation_history}`
   - `### Current Turn` ← `{round_index}`
   - `### Is New Session` ← `{is_new_session}`
4. **输出格式**：JSON 对象（`query`/`ground_facts`/`complexity`/`reasoning`/`new_session_hint`）

### 上下文依赖与并发互斥的关系

上述机制直接导致 dynamic 不支持并发 QA：

- 第 N+1 轮的查询**内容**由 LLM 基于前 N 轮的问答历史生成，无法提前计算。
- 即使能提前知道查询文本，回复也依赖前序对话在同一会话中的累积上下文。
- 因此 `run_generate_mode` 必须严格串行：生成查询 → 发送给 agent → 等待回复 →
  追加到历史 → 生成下一轮查询。

### replay 模式的上下文处理

replay 模式的查询来自外部数据集（`jobs`），不经过 `_generate_dynamic_query`，
不依赖 LLM 生成查询文本。但每个 sample 内的查询发送到同一 `qa_session`
（`workflows.py:257`），会话内上下文由 agent 自身累积--后续查询的回复受前序
查询及回复影响，同样无法并行。

### 跨会话记忆测试：概率性新会话生成

generate 模式在多轮对话中**概率性地创建新会话**，以测试 agent 的跨会话记忆
能力--agent 在新会话中丢失对话历史，必须依赖记忆系统召回之前会话中的信息。

#### 新会话创建机制（`workflows.py:171-179`）

每轮查询生成时，LLM 在输出 JSON 中包含 `new_session_hint` 布尔字段，建议是否
开始新会话。`workflows.py` 根据以下条件决定是否实际创建新会话：

```python
if (
    not session_id                                    # 首轮：尚无会话，必须创建
    or round_data["new_session"]                      # LLM 建议新会话
    and random.random() < args.new_session_ratio      # 且概率检查通过（默认 0.3）
):
    session_count += 1
    session_id = agent_plugin.create_session(
        title=f"test-{evaluator.theme}-s{session_count}",
    )
```

由于 Python 运算符优先级，`and` 优先于 `or`，实际逻辑为：
`(not session_id) or (new_session_hint and random < ratio)`

即新会话在两种情况下创建：
1. **首轮强制创建**：`session_id` 为空（第一轮，尚无任何会话）
2. **概率性创建**：LLM 建议 `new_session_hint=True` **且** `random.random()` 小于
   `--new-session-ratio`（默认 0.3，即 30% 概率）

`--new-session-ratio` 控制跨会话测试的频率：
- `0.0`：LLM 建议 new_session 时也永不创建新会话（仅首轮创建一个会话）
- `1.0`：LLM 每次建议 new_session 时都创建新会话
- `0.3`（默认）：约 30% 的 LLM 建议会触发新会话创建

#### 跨会话上下文的不对称设计

新会话创建后，**LLM 查询生成器与 agent 的上下文处理方式不同**：

| 组件 | 新会话后的上下文 | 效果 |
|------|----------------|------|
| LLM 查询生成器 | `previous_queries`/`previous_replies` **不重置**，仍包含所有历史轮次的问答 | LLM 知道之前讨论过什么，能生成引用跨会话信息的查询 |
| Agent | `create_session()` 创建全新会话，对话历史从零开始 | Agent 看不到之前会话的对话，必须靠记忆系统召回 |

这种不对称正是跨会话记忆测试的核心：用户（LLM 模拟）知道之前说过什么，但
agent 的新会话中没有对话历史，只能依赖记忆系统的召回能力来正确回答。

#### `is_new_session` 标志

传入 `generate_next_query` 的 `is_new_session` 字段值为 `not session_id`
（`workflows.py:151`）：

- **首轮**：`session_id` 为空，`is_new_session=True`，告知 LLM 这是全新开始
- **后续轮次**：`session_id` 已设，`is_new_session=False`，即使刚创建了新会话

该标志仅在首轮为 `True`，用于让 LLM 知道没有任何前序上下文。后续轮次中，LLM
通过 `conversation_history` 获得跨会话的完整问答历史，因此不需要额外的
"新会话"信号--LLM 自身建议了 `new_session_hint`，知道新会话可能被创建。

## 插件与 LLM 参数

所有插件均调用 `add_llm_args()` 声明 `--llm-*` 参数。`echo_agent` 走 EchoAgent
管线做 QA，不直接使用 LLM 客户端，但动态评测框架需要 `--llm-*` 参数做质量评估。
其他插件（`bare_llm`、`echomem_mcp`、`openviking_mcp`、`vikingbot`）自身也需要
`LLMClient` 做 QA 生成。委托给插件声明避免 `argparse` 重复声明冲突。

## 场景生成 LLM 与质量评估 LLM

dynamic 有两组 LLM 参数：

- **场景生成 LLM** (`--scenario-*`): 用于 generate 模式生成背景记忆和查询。由
  `run_eval` 自身声明，因为场景生成是动态评测特有逻辑，不属于插件。
- **质量评估 LLM** (`--llm-*`): 用于评估回复质量。由插件通过 `add_llm_args()`
  声明，因为不同插件都需要 LLM 做质量评估，委托给插件声明避免重复。

`--scenario-base-url`/`--scenario-api-key` 与 `--llm-base-url`/`--llm-api-key`
互补：一个有值另一个为空时，空的自动复制有值的（`resolve_llm_credentials`）。

### Judge 通用模式（shared/llm_client.py）

`LLMClient.chat` 提供三个对任何 MaaS 模型通用的传输层开关：

- `response_format`：请求 `response_format={"type": "json_object"}`，强制模型输出 JSON 对象；
- `thinking_disabled`：请求 `thinking={"type": "disabled"}`，关闭推理模型的思维链；
- `omit_max_tokens`：不发送 `max_tokens`，把输出预算交给 provider 默认值。

判题入口 `LLMClient.judge()` 与 `chat_with_repair()` 默认即 Judge 模式——强制 JSON、
关闭思考、不传 `max_tokens`（`thinking_disabled` 可作为参数外部覆盖）。理由：

- 推理模型会把 `max_tokens` 预算花在 `reasoning_content` 思维链上（实测 deepseek-v4-flash
  在 2048 预算下 `reasoning_tokens` 吃掉 1778，正文 JSON 被截断、`finish_reason=length`），
  导致判题输出无法解析；关闭思考后正文完整，实测 JSON 可正常解析。
- 不传 `max_tokens` 避免配置里的小上限截断长判定。
- 解析纯单词判定的评测（longmemeval 的 yes/no）不强制 JSON，显式传 `response_format=False`；
  关闭思考与不设上限仍对其生效。

三个带 LLM judge 的 benchmark（locomo / longmemeval / dynamic）均经由这两条入口，统一受益；
hotpotqa 用官方 F1/EM，无 LLM judge。

### 质量评估输出的 JSON 解析容错与失败判定

质量评估用评测 LLM 给每条回复打分，要求返回单个 JSON 对象。评测 LLM 输出不稳定，
`dynamic/metrics.py` 的 `_parse_evaluation_json` 按以下顺序逐级容错解析：

1. 剥离 markdown 代码围栏（```json ... ```）。
2. 从第一个 `{` 起用 `json.JSONDecoder.raw_decode` 精确解析**单个** JSON 值，
   避免贪婪正则把 JSON 之后的尾注（尤其带花括号的文字）一并吞入导致语法错误。
3. 仍失败则去除尾随逗号后重试 `json.loads`。
4. 再退化为 `ast.literal_eval`（先把 `true/false/null` 映射为 Python 字面量）。

以上全失败才抛 `ValueError`，交给 `shared/llm_client.py` 的 `chat_with_repair` 重试
（最多 3 次），每次重试追加 `build_dynamic_repair_prompt`（按实际维度列出完整期望
schema）并把温度抬到 0 以上，避免确定性请求复现同样的坏输出。

失败判定：某条回复解析失败时 `quality_score` 记为 `None`、`quality_error` 记录原因；
`dynamic/artifacts.py` 统计 `quality_evaluator_errors`，只要存在质量评估错误就把整个
运行标记为 `failed` 并 `exit 2`，结果不作为正式分数——`avg_quality_score` 只对成功
评分的行求平均，混入未评分行会高估正式分数，故宁可整体失败、由修复或重跑补齐。

| `--sample` | str | `all` | replay 模式 sample 筛选：`all`/sample 索引/sample_id。generate 模式始终只导出 1 个 sample，回放 dynamic 生成的数据集时此参数无实际效果；回放外部多 sample 数据集（如 LoCoMo 格式）时可选择特定 sample |
| `--questions` | int | `0` | replay 模式问题数（`0` = 全部） |
| `--evaluator-config` | str | `configs/evaluator_template.yaml` | 评估器配置 YAML |
| `--user-simulator-config` | str | `configs/user_simulator_default.yaml` | 用户模拟器配置 YAML |
| `--num-memories` | int | `5` | generate 模式：生成的背景记忆数 |
| `--num-queries` | int | `10` | generate 模式：生成的提问数 |
| `--new-session-ratio` | float | `0.3` | generate 模式：新会话比例 |
| `--typing-speed-ms` | int | `200` | 打字模拟速度（毫秒/字符） |
| `--typing-jitter-ms` | int | `20` | 打字模拟抖动（毫秒） |
| `--scenario-model` | str | `deepseek-v4-flash` | 场景生成 LLM 模型 |
| `--scenario-base-url` | str | `""` | 场景生成 LLM base URL |
| `--scenario-api-key` | str | `""` | 场景生成 LLM API key |
| `--out-dir` | str | `results` | 结果输出目录 |

> `--scenario-base-url`/`--scenario-api-key` 与 `--llm-base-url`/`--llm-api-key` 互补：
> 一方有值另一方为空时，空方自动复制有值方（`resolve_llm_credentials`）。因此只需配置一组。
