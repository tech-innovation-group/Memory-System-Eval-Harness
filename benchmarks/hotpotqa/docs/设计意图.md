# HotpotQA 失败诊断、检索轨迹与工具审计 设计意图

## 目标

为 HotpotQA 评测补齐 locomo 已有的三层元分析产物，使单次运行不仅给出官方指标，
还能回答三个问题：

1. **失败归因**（`diagnosis.json`）：答错的题属于哪类失败？是否可重试？
2. **检索轨迹**（`retrieval_traces.jsonl`）：每题检索到了什么、答了什么、归因是什么？
3. **工具审计**（`agent_traces/` + `tool_audits.jsonl/.json`）：agent 的工具调用行为。

与 locomo 的差异：HotpotQA **没有 LLM judge**，正确性不来自 judge verdict，
而来自官方指标 `eval_results.csv` 中的 `answer_em` / `answer_f1`。

## 接口

### `benchmarks/hotpotqa/qa.py`

- `_safe_question_id(question_id)`：question_id 归一化为安全文件名。
- `_write_trace(trace_dir, result)`：`result.trace` 非空时写 `agent_traces/<safe_id>.json`。
- `_tool_audit_rows(results)` / `_write_tool_audits(path, results)`：从
  `result.trace["tool_audit"]` 提取审计行，写 `tool_audits.jsonl` + `tool_audits.json`。
- `write_tool_audits(result_dir, results)`：resume 恢复 trace 后全量重写
  `tool_audits.jsonl/.json`，保证 resume 目录与从 0 运行等价。
- `run_hotpotqa_qa`：QA 过程中增量写 trace 与 tool audits（镜像 locomo）。

数据来源：`QAResult.trace` 由 `shared/benchmark_qa.py` 从 `resp.extra["trace"]` 填入。
documents 模式默认开工具：`vikingbot` 经 `answer_one_vikingbot_question(..., search_resources_mode=True)`
跑多轮工具循环（`memory_search`/`memory_read_many` 均指向 `viking://user/resources/`
语料，title 经 `path_title_map` 解析进 `SearchResult.metadata.hotpotqa_title`）；
`echomem_mcp` 经 `_send_documents_with_tools` 用 `LLMClient.chat_with_tools` 跑同样的
资源工具循环（title 经 `build_retrieval_items` 解析）。两插件关闭工具（`--no-tools`/
`--no-tool-calling`）时回退单次 RAG（`qa_profile=vikingbot_docs`/`echomem_mcp_documents`，
`iterations`/`tool_audit` 为空）。插件无 trace 时产物为空文件，属正常。

### `benchmarks/hotpotqa/resume.py`

- `copy_resume_traces(state, result_dir)`：把源运行目录 `agent_traces/` 中复用题的
  trace 文件复制到新结果目录（按 sanitized 文件名匹配，源目录取
  `state.source_csv.parent`）。
- `restore_resume_traces(results, result_dir)`：把复制过来的 trace 读回复用题的
  `QAResult.trace`（CSV 不存 trace），使 summary 的 trace 派生字段与 tool_audits
  覆盖整个 resume 后的运行。

### `benchmarks/hotpotqa/reporting.py`（summary 的 trace 派生字段）

与 locomo 对齐，`build_summary` 从 `QAResult.trace` 聚合：

- `tool_call_total`：`sum(result.tool_call_count)`
- `avg_iterations`：`result.iterations` 均值
- `served_model_ids`：各轮 `iterations[].model_response.response_model` 去重
- `tool_protocol_sha256`：`trace.tool_protocol.sha256` 去重
- `messages_jsonl_read_questions/calls/rate`：`trace.tool_audit.messages_jsonl_reads`
  或 `read_files` 中命中 `messages.jsonl` 的读取统计

### `benchmarks/hotpotqa/diagnosis.py`

- `classify_failure(qa_row, eval_row) -> dict`：单题失败分类。
- `build_diagnosis(qa_rows, eval_rows, jobs) -> (summary, traces)`：纯函数，汇总 + 逐题轨迹。
- `diagnose_run(qa_results_path, eval_results_path, dataset_path, sample, question_limit,
  output_dir) -> summary`：写 `diagnosis.json` + `retrieval_traces.jsonl`。
- `main()` CLI：对历史运行目录重新出诊断（`--questions` 与原运行一致以保证题集判定）。

### `benchmarks/hotpotqa/evaluate.py`

- `extract_answer(response, gold) -> str`：打分前从散文回复中抽取简洁答案。HotpotQA 的
  gold 是短字符串，EM/F1 对多余词零容忍，而模型常输出完整句子。分层（顺序不可调换）：
  1. 回复归一化后首词为 `yes`/`no`/`noanswer` 且 gold 也是 yes/no 型 → 返回该词
     （gold 非 yes/no 时不触发，避免 "Yes, ..." 开头把正确长答案误杀）；
  2. gold 的归一化 token 是回复归一化 token 的**连续子序列** → 返回 gold
     （连续子序列而非字符串子串，避免单 token gold 如 `no` 命中 `know`）；
  3. 在**原始文本**上剥离常见前导语（"the answer is"、"according to ..."、
     "based on the retrieved documents"、"i think/believe" 等，最多 3 轮）后
     取第一分句并归一化；
  4. 兜底返回原文。
- `evaluate_hotpotqa` 在 `answer_metrics` 前调用 `extract_answer`，并把抽取结果写入
  `eval_results.csv` 的 `answer_extracted` 列（可审计）。`answer_metrics` 本体不变，
  `qa_results.csv` 仍保留原始 response。

### `benchmarks/hotpotqa/import_memory.py` + `run_eval.py`（--reuse-memory-from）

`--reuse-memory-from <源运行目录>` 复用先前运行的**记忆**（身份 + 已导入语料），但
**全新重跑全部 QA**，与 `--resume`（复用健康 QA 答案）语义不同：

- `run_eval`：`reuse_source = args.resume or args.reuse_memory_from`；
  `apply_resume_memory_identity` 从源运行的 `qa_resume_manifest.json` 载入身份；
  QA 阶段**不**设置 qa_resume_state（只有 `--resume` 才复用 QA 答案），因此全部题重跑。
- `import_hotpotqa_memory(..., reuse_memory=True)`：documents 模式不调用
  `add_resource`（语料已在该身份下），仅用 `build_document_corpus(plans)` 从数据集
  重建 path→title 映射（确定性），`import_results.csv` 记 `reused` 状态
  （在 `SUCCESS_STATUSES` 中，计入 completed）。
- `--resume` 的 documents 模式同理：`prior_import_rows` 中已完成的 `documents`
  批次命中 `completed_map` 时跳过重新注入，仅重建 path→title 映射并记 `reused`；
  否则（首次 documents 导入）走 `import_hotpotqa_documents` 全量注入。
- summary：`memory_source="existing"`，`evaluation_identity.mode="reused"`，
  新增 `summary.memory_reuse = {enabled, source}`。

## 行为约束

### vikingbot 各模式的最终回答必须精确简短

`vikingbot` 的人设（默认 agent 人设与 v0.4.11 个人助手人设）默认输出解释性散文，
与 HotpotQA 的 EM/F1 评测不匹配（F1 的 precision 项对多余词零容忍：多轮检索
recall 上升但 EM/F1 反而骤降）。因此 vikingbot 的 benchmark 回答路径
（documents+tools 的 `_answer_documents_with_tools` 与其余模式的 `send_message`）
统一把 `_BENCHMARK_ANSWER_APPEND`（"answer with only the exact answer"）拼进
`system_prompt_append`，与外部传入的 append 拼接后追加到 system 消息。
`echomem_mcp` 工具路径的 system prompt 本身即 `RESOURCE_SYSTEM_PROMPT`。实测
（2026-08-18 documents 模式）证明 "concise" 类措辞压不住模型的散文输出：1000 题
EM 仅 7.7%，923 个失败中 760 个的 gold 完整出现在回复里。因此
`RESOURCE_SYSTEM_PROMPT` 与 echomem_mcp 的 `_SYSTEM_PROMPT` /
`_NO_TOOLS_SYSTEM_PROMPT` 均改为显式要求「只输出答案本身，yes/no 只输出
yes/no」，并在评测侧用 `extract_answer` 做兜底抽取。

### classify_failure 判定顺序（不可调换，前序命中即短路）

1. `answer_em == 1` → `correct`
2. `llm_error` 非空 → `model_error`（retryable）
3. `retrieval_error` 非空 → `retrieval_error`（retryable）
4. response 为空 → `empty_answer`（retryable）
5. 无 retrieval items → `empty_retrieval`（retryable）
6. `answer_f1 > 0`（EM=0）→ `partial_answer`
7. gold 答案 token 出现在检索证据中 → `evidence_unused`
8. 有检索证据但无 gold 重叠 → `evidence_mismatch`
9. 无任何证据 → `memory_missing`

- **正确判定用 EM 而非 F1**：与 HotpotQA「accuracy = answer EM」的惯例一致；
  F1 > 0 但 EM = 0 记 `partial_answer`（部分命中，非硬失败，不可重试）。
- `retryable` 仅对基础设施类失败（model/retrieval/empty answer/empty retrieval）为真，
  语义类失败（partial/evidence_*）不可通过重跑解决。
- 真实数据中报错题的 EM 必为 0（evaluate 基于空 response 计算），因此 1 在 2 之前
  不会误判；测试数据必须保持这一一致性。

### build_diagnosis

- traces 逐题包含官方指标（answer/supporting-facts 的 EM/F1）、检索 items、归因字段。
- summary：`accuracy` 为 EM 口径正确率；`retrieval_coverage` 为「有非空检索证据」占比；
  `failure_breakdown` 按失败 mode 计数（question_ids 截断 20）；`category_breakdown`
  按 hotpotqa 题型（comparison/bridge）分桶；`missing/unexpected/duplicate` 用于
  排查运行完整性。

### diagnose_run 的题集一致性

expected 题集 = `load_dataset(sample)` + `select_jobs_and_plans(limit=question_limit)`，
与 `run_eval` 的选择逻辑一致。这样 `--questions N` 限流运行时，`missing_question_ids`
不会把「未运行的题」误报为缺失。

## 边界条件

- 无 judge：`eval_results.csv` 缺失时 eval_rows 为空，所有题按无指标行处理
  （EM/F1 取 0），分类退化为错误/空/证据类判定。
- 插件无 trace：`agent_traces/` 无文件，`tool_audits.jsonl/.json` 为空文件。
- 空证据：`_gold_evidence_overlap` 对无证据返回 False，最终落入 `memory_missing`。
- 限流运行：`diagnose_run` 必须传入与原运行一致的 `--questions`，否则 missing 判定失真。
- resume：复用题的 trace 从源运行目录复制并读回（`copy_resume_traces` +
  `restore_resume_traces`），随后 `write_tool_audits` 全量重写，保证 resume 目录
  与从 0 运行的目录等价（复用题也有 agent_traces 与 tool_audits）。源运行目录
  无 `agent_traces/`（旧版本产物）时复制数为 0，不报错。
- reuse-memory-from：源运行目录必须含 `qa_resume_manifest.json`（否则身份不复用，
  记忆会在新身份下找不到）。documents 模式复用后 QA 检索的是源身份下的既有语料；
  若后端数据已清理，检索会为空，诊断会落在 `empty_retrieval` / `memory_missing`。
  `--reuse-memory-from` 与 `--resume` 同用时 `--resume` 优先。
