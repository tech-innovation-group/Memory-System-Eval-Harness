EchoMemory 外部接入操作指南

这里只保留纯文字说明。先明确两点：不是所有后端都只给一个端口就能接；EchoMemory 的图结构和检索逻辑留在后端内部，平台只调用统一导入与检索接口。

重点：不要把 EchoMemory 理解成“只要给平台一个端口就能接”。当前 EchoMemory 是本地 SDK + 源码目录 + workspace 的接法。

重点：不要一上来全量跑。先导入 conv-30，先测 5 到 10 题，确认检索、回答和判分都通，再扩到正式数据。

重点：真实密钥只放在 .env.local 或页面密码框。不要写进日志、报告、提交记录或共享说明。

接入结论
  • OpenViking 偏 HTTP 服务型，对接重点是 host / port。
  • EchoMemory 当前按本地 SDK + 源码目录 + workspace 对接，不是单独暴露一个统一检索端口。
  • 大多数外部接入不需要改 Web 检索逻辑。
默认数据路径
  • 优先读取 LOCOMO_DATA。
  • 其次读取 dataset/full/locomo.json。
  • 再回退到 dataset/locomo.json 和 dataset/locomo10.json。
外部团队真要改代码
  • 优先看 scripts/echomemory_common.py。
  • 任务拼装和默认 QA 参数在 memory/plugins/echomemory/tasks.py。
  • 如果只是换密钥、workspace、模型地址，不需要改平台代码。
步骤 1. 先在系统配置切到 EchoMemory
  • 当前账户的记忆后端切到 EchoMemory。
  • 确认 EchoMemory 源码目录能被识别，workspace / account / user / agent 是本机要跑的值。
  • 至少把 Agent、判分、记忆注入模型做一次连通性测试。

关键检查：当前账户后端必须已经切到 EchoMemory。如果这里还是 OpenViking，后面的导入和 QA 会走错链路。

步骤 2. 先导入 conv-30，不要一上来全量跑
  • 先校验 LoCoMo JSON。
  • 推荐先导入 conv-30。
  • EchoMemory 导入模式先用“快速注入（推荐）”。
  • 优先勾选自动生成新的 workspace，避免污染旧记忆空间。
  • 导入完成后看 expected_messages、submitted_messages、commit_session 和完整性状态。

关键检查：完整性检查没过时，不要继续做 QA。先回头处理 workspace、会话提交或消息缺失。

步骤 3. 问答测试先跑 5 到 10 题，再判分
  • 对话范围先选 conv-30。
  • 先跑 5 到 10 题，确认每题都能产出回答、上下文和相关记忆。
  • 确认回答模型能返回结果，再跑判分，最后导出 HTML 报告。
  • 如果要测正式数据，再从小样本扩到全量。

关键检查：回答模型不通时，不要先怀疑 EchoMemory 检索。先确认模型地址、模型名、密钥和超时配置。

平台到底要求 EchoMemory 提供什么
  • 写入：create_session、add_message、commit_session
  • 检索：find、search
  • evidence 至少能提供 content，以及 uri/source_uri、score/confidence 这一类字段
平台不关心什么
  • 图结构怎么建
  • 向量索引怎么切分
  • find / search 内部怎么路由
  • 是图召回、向量召回还是混合召回

1. 项目与运行环境
  • 项目目录：当前 locomo-eval-web 或外发后的同名目录。
  • Python：建议 Python 3.11+，能直接运行 server.py。
  • 浏览器入口：打开 http://127.0.0.1:19181/，不要直接打开 HTML 文件。
2. LoCoMo 数据集
  • 项目内置数据集放在 dataset/，由 dataset/manifest.json 注册。
  • 在“数据集”页选择卡片后点“校验数据集”；不需要用户单独下载或填写本机绝对路径。
  • 支持 LoCoMo 列表格式 JSON；如果不是 10 个对话，也应该能校验出样本数、问题数和分类分布。
3. 记忆后端
  • 当前交付只包含 OpenViking 基线和 EchoMemory 接入。
  • OpenViking：作为基线对照，填写服务地址、端口、workspace 和 account。
  • EchoMemory：作为外部接入主线，填写 ECHOMEM_ROOT、workspace、account、user、agent。
  • 系统配置页先点“运行预检”，确认记忆后端、workspace、数据集和模型配置都可用。
  • 每次正式实验建议使用新的 workspace 或新的 account，避免历史记忆污染。
4. 模型配置
  • 向量模型：EchoMemory 抽取和检索需要 embedding provider。
  • EchoMemory SDK：ECHOMEM_ROOT 必须指向包含 packages/echomem/src 和 packages/echofs/src 的源码目录。
  • 回答模型/判分：使用兼容 OpenAI Chat Completions 的地址、模型和密钥。
  • API 密钥 只填到本机 .env.local 或 Web 密码框，不要写进报告、日志或截图。
5. 输出与安全
  • 评测输出：项目下的 runs/，外发目录中不应包含历史运行结果。
  • 空间与后端状态：runs/accounts.json，不保存 API 密钥。
  • 长期记忆落盘：OpenViking 在 workspace 下，EchoMemory 在 EchoMemory workspace 下。
  • 每次任务通常包含日志、结果文件、摘要和 HTML 报告文件（report.html）。

跑通流程

按顺序执行，方便定位问题。

1 预检并启动服务

先运行 ./preflight.sh，通过后再启动 Web，并打开 /health 确认服务可用。

2 记忆导入

填写 LoCoMo JSON，校验数据集，选择 conv，导入并检查完整性。

3 问答测试

选择单题、多题、时间题或错题，查看回答、Token 用量和相关记忆。

4 判分

运行判分模型，显示进度、待判分数量和补跑入口。

5 查看报告

导出 HTML 报告，查看历史报告，并选择多次任务做对比。

记忆服务接入要求
  • 能创建/追加会话消息，并在需要时生成长期记忆。
  • 归档后记忆应落在当前空间对应的目录下面。
  • 问答阶段要能返回答案、用量、证据记忆和日志。
  • 如果 EchoMemory fork 改了图记忆模块，优先保证 evidence 结构稳定，这样报告和详情页才能继续展示。
EchoMemory 接入接口
  • open_runtime 用于加载 EchoMemory runtime 配置。
  • create_session、add_message、commit_session 负责导入和归档。
  • find / search 负责 QA 阶段相关记忆检索。
  • 图记忆模块可以放在 EchoMemory 内部实现，平台只消费统一 evidence 结构。
外发包不应包含
  • runs/ 历史运行结果和日志。
  • judge.conf、.env.local、真实 runtime yaml。
  • OpenViking / EchoMemory workspace。
  • 任何真实 sk-...、Bearer 密钥或模型服务密钥。
外发前扫描
  • 在交付目录运行密钥扫描，确认只出现占位符。
  • 保留 env.echomem.example，不要保留 .env.local。
  • 如需分享报告，先确认报告里没有密钥、私有路径或敏感业务数据。

常见问题

先定位到数据、服务、模型或判分。

页面打不开

确认不是 file://，然后检查 /health。如果 health 不通，重启 server.py。

记忆后端连接失败

OpenViking 先检查服务地址和端口；EchoMemory 先检查 ECHOMEM_ROOT、依赖环境和 workspace 权限。

准确率为空

问答完成但还没判分时会显示“待判分”。先运行判分，再看准确率。

EchoMemory 检索为空

确认导入和 QA 阶段使用相同 workspace、account、user、agent；任一项不同都会变成干净记忆空间。

记忆不完整

看导入摘要、会话目录、历史文件和长期记忆文件；必要时换干净目录重新导入。
