EchoMemory vs OpenViking HotpotQA 分析

更新时间：2026-06-30。目标：解释 EchoMemory 和 OpenViking 差距大的原因，解释 EchoMemory 为什么慢，判断这个数据集是否需要记忆注入，并记录当前改进方向。

结论摘要

  • 当前差距不是单一问题。 既有 vikingboat_lite + no tool loop 的模式错配，也有 HotpotQA 第二跳检索抓不到桥接实体的问题。
  • EchoMemory 慢的主因不在 QA 本身。 当前 500 题运行态里，平均写入注入约 118.8962s，平均 settle 等待约 80.4617s，而平均 QA 约 44.4599s。
  • 这个 HotpotQA 跑法当前是需要记忆注入的。 现有 EchoMemory 路径先把每题 10 篇 context 文档写进 EchoMemory，再依赖 EchoMemory 检索来回答。
  • OpenViking 的路径更短。 它更接近“当前题 source documents 直接物化到 document memory，再检索这些文档”。

为什么 EchoMemory 这么慢

  • 当前 HotpotQA 的 benchmark_adapter.hotpotqa_job_plan() 会把每题 context 拆成 10 篇 memory_documents。
  • echomemory_generic_qa.import_messages_from_plan() 会把每篇文档包装成一条 [benchmark memory] 消息注入 EchoMemory。
  • 每题 QA 前还会走 wait_for_async_memory_stability()，必要时触发 repair；所以耗时主要花在导入、原子化、图/向量稳定，不是回答模型本身。
  • 当前正式 500 运行状态也卡在 waiting_async_memory_settle，说明瓶颈仍在异步记忆稳定链路。

这个数据集需要记忆注入吗

问题答案
当前 EchoMemory 实现是否需要？需要。 现在不是直接读原始 HotpotQA context，而是先写入 EchoMemory 再检索。
HotpotQA 任务本质是否必须需要？不必须。 HotpotQA 本质是给定当前题文档做多跳问答，不天然要求长期记忆系统的 commit / stabilize / repair。
这意味着什么？如果目标是测 EchoMemory 作为记忆后端，这条链是合理的；如果目标只是追求 HotpotQA answer-only 上限，这条链会额外引入时延和噪声。

当前 HotpotQA 记忆注入流程

  1. 拆题：hotpotqa_job_plan() 从每题 context 生成 10 篇 memory_documents。
  2. 转消息：import_messages_from_plan() 把每篇文档转成一条 [benchmark memory] 消息，附带 sample_id、document_index、title。
  3. 写入 EchoMemory：import_sample_memory() 调 SDK 提交消息。
  4. 等待稳定：wait_for_async_memory_stability() 轮询 commit / overview / abstract / atom / graph / vector；必要时 repair。
  5. 再做 QA：answer_question() 基于 EchoMemory 检索结果构造 prompt 并回答。
HotpotQA JSON
  -> hotpotqa_job_plan()
  -> memory_documents (10 docs/sample)
  -> import_messages_from_plan()
  -> import_sample_memory() / EchoMemory SDK
  -> wait_for_async_memory_stability() / optional repair
  -> answer_question()
  -> EchoMemory retrieval
  -> LLM answer
  -> HotpotQA answer-only EM/F1

当前修复方向

  • 已加：非 tool-loop 模式下的 direct-answer prompt 约束。
  • 已加：最终答案清洗，过滤 memory_search、DSML、XML、search intent。
  • 已加：基于命名实体和缺失关系词的 follow-up retrieval query。
  • 进行中：当非 tool-loop 模式答成工具样文本或 unknown 时，自动做一次受限 tool-loop rescue。
  • 待验证：这些改动能否在代表性污染题上稳定提升 answer-only EM/F1。
