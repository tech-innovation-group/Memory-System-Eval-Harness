记忆注入流程

  1. 拆题：hotpotqa_job_plan() 从每题 context 生成 memory_documents。实现位置：scripts/benchmark_adapter.py:786，文档生成在 collect_hotpotqa_documents()（:750）。
  2. 转消息：import_messages_from_plan() 把每篇文档包装成一条 [benchmark memory] 消息。实现位置：scripts/echomemory_generic_qa.py:175。
  3. 写入 EchoMemory： 运行器先完成 import / settle / repair，再把该题送进 QA；相关记录会回填到 import_session_id、import_status、memory_injection_time_s。实现位置：scripts/echomemory_generic_qa.py:866。
  4. 做召回：answer_question() 完成 retrieval 后，把命中的 hits 同时写进 relevant_memory 和 qNNN .recall.json。实现位置：scripts/echomemory_memory_qa.py:3050 和 :3088。
HotpotQA JSON
  -> hotpotqa_job_plan()
  -> collect_hotpotqa_documents()
  -> import_messages_from_plan()
  -> EchoMemory import / settle / optional repair
  -> answer_question()
  -> relevant_memory + retrieval_count + qNNN.recall.json
  -> answer-only EM/F1

为什么准确率低

原因当前证据影响
最终答案污染 当前正式 39 行里，按直接模式匹配，至少 12 行输出里残留了 memory_search、DSML、函数调用，或者“根据记忆中的信息 / let me search”式文本。 在 HotpotQA answer-only EM/F1 口径下，哪怕 evidence 是对的，这种输出也会直接掉分。
second-hop 证据不稳 5a8c7595554299585d9e36b6 在 probe3 里已经能召回 Shirley Temple 文档，且该文档包含 Chief of Protocol，但最终仍答成 United States ambassador to Ghana。 说明问题不是简单“没召回”，而是多候选属性值没有被正确选中。
少数题确实空召回 5a85b2d95542997b5ce40028 在正式 500 当前样本里 retrieval_count=0，属于真实的 retrieval empty；但在 probe3 里同题已经变成 retrieval_status=ok、答案正确。 说明 query / follow-up retrieval 的改进对部分题有效，但正式运行的旧样本里还保留着空召回问题。
这条架构给 HotpotQA 额外加噪 当前实现是“每题先写 EchoMemory，再等稳定，再检索回来”；不是直接在原始 context 上做问答。 相比直接 document QA，多了一层 import / settle / rerank / prompt 对齐噪声，也显著拖慢速度。

为什么说主因不是“完全没召回”

  • 正式 500 当前样本：36/39 行 relevant_memory 非空。
  • 正式 500 当前样本：36 行 retrieval_status=ok，只有 3 行是 empty。
  • probe3 当前已经拿到 66.67% / 66.67% 的 3 题 answer-only 结果，且三题全部 retrieval_status=ok。

所以更准确的说法是：当前 EchoMemory 在 HotpotQA 上的问题是“召回 often works, but not stably enough for multi-hop answer selection”，而不是“召回系统整体坏了”。

建议的下一步

  1. 继续压最终答案污染：把 tool-like / search-like 文本从最终 response 中彻底去掉。
  2. 继续加强 second-hop query 组织：尤其是 bridge 题里的“实体 -> 属性” follow-up 查询。
  3. 把正式 500 旧样本和 probe3 新样本按同题做 before/after 对照，专门看“空召回修复”和“仍然答错但已非污染”的两类题。
  4. 如果目标是纯 HotpotQA answer-only 上限，需要重新评估“每题先 commit 到 EchoMemory 再搜回来”这条架构是否值得保留。
