EchoMemory 检索记忆修复方案

面向 tech-innovation-group/Memory-System-Eval-Harness 使用者的 LoCoMo QA 修复说明。目标不是只补日志，而是确保正式 QA 运行时真的检索并写入记忆。

日期 2026-06-29 范围 EchoMemory + LoCoMo QA 问题类型 recall 文件存在但 selected 为空

1. 现象与根因

当前问题不是“没有生成 recall 文件”，而是“生成了 qNNN.recall.json，但里面没有实际检索到的记忆”。典型表现如下：

qa_memory_injection_enabled = false
prompt_mode = one_shot
uses_retrieved_memory = false
retrieval_ok_count = 0
retrieval_empty_count > 0
selected_count = 0
selected = []

这类 run 会给人一种“系统有 recall 日志”的错觉，但实际上只是写出了空的 artifact。根因主要在于 QA 默认参数和任务构造入口不一致，导致部分入口仍然会回落到不适合正式 LoCoMo 评测的模式。

2. 目标状态

正式的 EchoMemory LoCoMo QA 至少应满足下面这组条件：

qa_memory_injection_enabled = true
prompt_mode = vikingboat_lite
memory_tool_loop_enabled = true
retrieval_ok_count > 0
qNNN.recall.json.selected_count > 0
qNNN.recall.json.selected[*] 包含 uri / score / memory_type / preview
judge_summary.json.uses_retrieved_memory = true
一句话：要修的是“正式 QA 的默认运行链路”，不是单独补一个日志打印函数。

3. 必改文件

文件 必须修改的点 原因
memory/services/task_orchestrator.py
  • 对 echomemory_qa + locomo 做 payload 归一化
  • 空值或 one_shot 的 prompt_mode 强制改为 vikingboat_lite
  • qa_memory_injection 默认强制为 true
  • vikingboat_tool_loop 在 LoCoMo 正式 QA 下默认开启
 统一入口默认值，避免 UI payload、旧配置或空配置把任务带回空检索模式。
memory/plugins/echomemory/tasks.py
  • 把 QA 命令构造层默认 prompt_mode 从 one_shot 改成 vikingboat_lite
  • 非法值 fallback 也不要回落到 one_shot
  • qa_memory_injection 默认值保持 true
 这是最终生成命令的地方。只改 UI 或 orchestrator 不够，其他入口仍可能绕过前置归一化。
memory/task_specs.py
  • Retry failed EchoMemory QA 的默认 prompt_mode 不要使用 one_shot
  • --qa-memory-injection 默认开启
 否则正式任务修好了，重跑失败题时又会重新产出空 recall。
scripts/retry_failed_echomemory_qa.py
  • CLI 默认 --prompt-mode 改成 vikingboat_lite
  • 若收到 one_shot，在构造命令时归一到 vikingboat_lite
 脚本级 retry 入口与平台级入口保持一致，避免“主流程有 recall，retry 没 recall”。

4. 建议一起补的保护

4.1 QA 前导入完整性 gate

在 memory/services/task_orchestrator.py 的 QA 启动前检查里增加正式 gate：

  • status == "complete"
  • session_complete_count == session_total_count
  • conv_complete == true

不满足时直接拒绝启动正式 QA，并提示先完成完整记忆导入。

4.2 平台级完整性标志

在 memory/plugins/echomemory/inspector.py 中补充并输出：

  • session_complete
  • session_complete_count
  • session_total_count
  • conv_complete

这样平台才能分辨“目录存在”与“该 conv 的导入已经可用于正式 QA”。

为什么这个保护重要：如果记忆还没完整导入就开始 QA，即使任务能跑完，也很容易生成大量 selected_count = 0 的假 recall 结果。

5. 可选增强：实时打印检索到的记忆

在 scripts/echomemory_memory_qa.py 中增加 log_retrieved_memory_preview()，把每题的 top hits 打到 stdout，是有帮助的，但它只是调试增强：

  • 适合快速观察“这题到底召回了什么”
  • 不改检索逻辑，不改模型输入，不改后端接口
  • 不能替代前面那组默认值修复

换句话说，日志打印解决的是“可见性”，不是“有效 recall 为空”的根因。

6. 推荐修改顺序

  1. 先改 task_orchestrator.py，统一入口默认值。
  2. 再改 memory/plugins/echomemory/tasks.py，堵住命令构造层的默认值回落。
  3. 同步改 memory/task_specs.py 和 scripts/retry_failed_echomemory_qa.py，让 retry 路径与主路径一致。
  4. 补导入完整性 gate 和 inspector 标志，防止导入不完整时误跑正式 QA。
  5. 最后再补实时日志打印，作为调试和排查增强。

7. 验收标准

修复完成后，至少要检查以下 artifact 和指标：

检查项 预期
summary.json qa_memory_injection_enabled = true，prompt_mode = vikingboat_lite，retrieval_ok_count > 0
judge_summary.json uses_retrieved_memory = true
q001.recall.json 等 selected_count > 0，并且 selected 内有 uri / score / memory_type / preview
导入完整性 session_complete_count == session_total_count 且 conv_complete = true 
{
  "selected_count": 14,
  "selected": [
    {
      "uri": "echo://.../overview.md",
      "score": 0.812,
      "memory_type": "session_summary",
      "preview": "..."
    }
  ]
}

8. 给他人的一句话说明

不要只补 “打印检索记忆到日志” 的代码。真正要修的是 EchoMemory LoCoMo QA 的默认运行链路：qa_memory_injection=true、prompt_mode=vikingboat_lite、tool loop 默认开启、导入完整性未达标时禁止正式 QA。否则仍然会继续产出“有 recall 文件但 selected 为空”的假 recall 结果。
