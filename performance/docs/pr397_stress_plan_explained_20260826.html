EchoMem PR397 压测方案

通俗说明、执行顺序、判定标准，以及结合真实模型测试结果的改进意见
代码：EchoMem PR397 当前代码 commit：24d3b9c0b782 方案基线：4U8G 单实例服务化 整理日期：2026-08-26

PR397 先做了什么

PR397 的核心目标，是解决多个租户同时提交记忆时，commit 任务无限堆积、拖慢在线 search，或者服务重启后状态不一致的问题。

它的整体思路不是把 commit 和 search 合成一个队列，而是把它们拆成不同的处理路径，并给 commit 增加排队上限、租户配额、同一 session 串行执行和故障恢复控制。

用一句话概括

PR397 = commit 有界排队 + 多租户限流 + commit/search 进程内资源隔离 + 熔断与状态恢复。

具体做法

问题PR397 的处理方式通俗理解
commit 请求无限堆积 给 commit executor 增加最大队列深度，队列满时拒绝新的显式 commit，并返回可重试的错误。 队伍太长时不再让所有人继续排队，而是告诉客户端稍后重试。
单个租户占满资源 增加租户级 commit quota，限制一个租户同时占用的 commit 数量。 一个客户不能把整台机器的处理能力全部占完。
同一个 session 同时提交 同一写入 scope 的 commit 通过执行链串行化，避免两个 commit 同时修改同一份 cursor 或索引。 同一份账本只能按顺序记账，不能两个人同时改。
commit 拖慢 search commit 和 recall 使用不同的 executor、准入 semaphore、provider 线程池和熔断器。 两条业务路径在进程内分开排队，commit 忙时尽量给 search 保留处理名额。
模型服务挂起或报错 对 LLM 和 embedding 增加超时、并发准入和 circuit breaker，连续失败后快速失败，避免线程和请求无限卡住。 模型服务坏了以后，不让所有请求一直堵在门口。
进程中途重启 通过 commit journal、cursor 和状态记录区分未完成 commit 与终态 failed，并按 local/cluster 模式执行收敛或恢复。 重启后先查账，知道哪些已经完成、哪些中断、哪些需要重新提交。

commit 和 search 实际上怎么走

commit 请求
→
commit executor
→
commit lane
→
LLM 抽取 / embedding / 写索引
search 请求
→
recall service
→
recall lane
→
检索 / embedding / 读取索引

因此，PR397 已经做了两条异步调度路径。但这不是完全的物理隔离：默认情况下，commit 和 recall 仍可能共享模型 endpoint、embedding provider、索引文件、CPU 和内存。后面的 S3 压测就是要验证这种“进程内隔离”是否足够，以及共享资源是否仍会互相影响。

PR397 没有完全解决什么

  • 没有默认保证 commit 和 recall 使用不同的模型账号、endpoint 或 provider 配额。
  • local 模式重启后主要是收敛中断状态，不等于自动重新执行失败的 commit。
  • 已经进入终态 failed 的 commit，通常需要客户端显式重提，不能直接说成后台自动补齐。
  • 如果 embedding provider 本身排队或超时，commit/search 的本地 lane 隔离仍可能无法消除外部服务的限流影响。

先说结论

PR397 的核心方向是合理的：验证高峰提交、查询不被拖垮、模型故障后能否恢复、进程重启后是否丢数据。

但当前方案还不能直接作为“通过/不通过”的最终测试规范。主要问题是：真实模型性能测试与故障注入测试混在一起；部分 SLO 没有明确统计口径；local 模式和 cluster 模式的恢复语义不同，却容易被读成同一种“自动恢复”。

结合之前真实模型测试，必须先增加“环境与配置预检”：PR397 的不同 engine 使用不同的 api_key_env，只设置顶层 key 会导致全部注入失败；DashScope 端点不接受 deepseek-v4-flash-0731，只能把该模型用于支持它的 QA/Judge 端点，EchoMem 注入模型要按实际端点支持列表配置；embedding 还出现过 provider admission 等待超过 30 秒的问题。

一、这次压测到底要回答什么

问题 1：会不会丢提交

高峰期大量 session 同时 commit，服务器可以拒绝或排队，但最终不能静默丢消息。

问题 2：提交时还能不能查

commit 很忙时，search/recall 仍要有明确的延迟和错误率上限。

问题 3：出故障能否恢复

模型挂起、进程被杀、服务重启后，要明确哪些由客户端重试，哪些由服务自动接管。

二、测试前必须固定的条件

项目建议固定值为什么要固定
代码 PR397 merge base、PR commit、工作区快照三者都记录 develop 更新会让同一个 PR 的结果失去可比性。
机器 4 vCPU / 8 GB，记录 CPU、RSS、磁盘、文件描述符 压测结果必须能说明是代码瓶颈还是机器规格造成的。
EchoMem 模型 按 config.example.json 的 engine 配置逐项解析；注入模型和 QA/Judge 模型分别记录 不能只看顶层 model.llm，也不能把 QA 模型名直接覆盖到所有 EchoMem engine。
并发 先 1/1 单并发验证正确性，再逐级增加 前面测试出现 embedding admission timeout，说明直接上高并发会把配置/供应商问题放大成假故障。
数据完整性 每条消息记录 message_id、content_hash；每个 archive 记录终态 “请求返回 202”不等于消息已经成功写入记忆。

必须新增模型与配置预检门禁：

  1. 读取实际运行的 config，而不是测试平台旧模板。
  2. 枚举所有 api_key_env，检查环境变量都存在且不为空。
  3. 对每个实际使用的 LLM/embedding endpoint 做一次最小真实请求。
  4. 检查模型名是否被该 endpoint 支持；不支持就停止测试，不进入压测。
  5. 记录 provider 响应时间、HTTP 状态码、模型名和配置摘要，但不记录 API key。

三、六个压测场景怎么理解

S1：基线测试，先知道“正常速度”

做法：单租户、4 个 session，持续写入并定期查询，持续约 30 分钟，不注入故障。

看什么：commit 成功率、commit P95、search P99、平均队列深度、CPU/RSS、线程数和文件描述符。

作用：后面所有场景都和 S1 对比。例如 S3 的 search 变慢 2 倍，必须以 S1 的同口径结果为基准。

需要改进：S1 里“每累计 1000+ 字符触发 auto-commit”会引入触发时机不稳定。建议同时保留一组固定频率的显式 commit，避免把 auto-commit 抖动和服务性能混为一谈。

S2：多租户 commit 风暴，验证背压

做法：8 个租户同时发起 160 个显式 commit，故意超过队列和租户配额，客户端收到 429 后按照 Retry-After 退避。

正确预期：出现 429 不代表失败，前提是拒绝原因正确、带退避信息，并且客户端最终重试成功。

通过条件：消息全集最终出现在 committed cursor 或 atom 的 source_turn_ids 中；没有重复 transcommit；热租户不能占满全部资源。

需要改进：“队列深度达到 256 后才允许出现 429”过于依赖内部实现细节。建议把它改成：记录达到饱和的时间点，检查饱和后拒绝是否符合策略；不要要求每次都精确达到某个瞬时数字。

需要改进：160 个 commit 的请求量能证明拒绝逻辑，但不一定能证明 4U8G 的长期容量。应增加 5 分钟稳定负载档位，例如 1、2、4、8 RPS，分别观察排队是否收敛。

S2b：只走 auto-commit，验证内部退避语义

做法：只写消息，不主动调用 commit，观察 auto-commit 遇到队列满时如何退避。

重要理解：当前设计中 add_message 不应该因为 auto-commit 队列满而返回 429；auto-commit 只是记录 deferred 并稍后尝试。

需要改进：末次写入后没有新活动时，最后一批消息可能保持未提交。这是当前语义缺口，不能在报告里写成“自动恢复成功”；应单独列为已知限制，或增加 idle flush/定时扫描机制后再验收。

S3：commit 和 search 隔离，避免“写一忙全站都慢”

做法：在 commit 风暴期间持续发 search，比较同租户与跨租户的延迟和错误率。

当前 PR397 能证明的范围：gateway 的准入容量、熔断器和部分 intent 路径隔离。

不能直接宣称：“commit 使用一个模型账号，recall 使用另一个模型账号，二者完全隔离”。PR397 当前部分 recall 路径仍可能和 commit 共用同一个 model proxy。

需要改进：search 的“成功”不能只看 HTTP 200。必须同时记录是否走了真实 recall、召回条数、deadline、模型请求是否发生，否则可能出现“没有调用模型所以很快”的假通过。

S4：模型故障注入，验证错误分类和重试

做法：依次注入 50% 的 500、完全挂起、恢复 provider，再观察熔断、失败终态和客户端重提。

应当区分三件事：

  • 客户端收到 429 后退避重试。
  • auto-commit 自己发现队列满后的内部退避。
  • 进程崩溃后由 cluster recovery 接管未完成 commit。

需要改进：故障注入用 mock provider 是合理的，因为需要稳定复现 500、429、挂起；但它不能替代真实模型容量测试。报告必须明确标注“真实模型性能结果”和“可控故障语义结果”是两类证据。

需要改进：“失败后自动补齐”表述不准确。单次 commit 进入终态 failed 后，local 模式不会后台自动重提，通常需要客户端显式重提；不要把它和 cluster 对非终态 commit 的 recovery 混为一谈。

S5：重启恢复，验证进程被杀后是否丢数据

做法：commit 正在执行时强制杀掉进程，等待后重启，分别测试 local 和 cluster。

模式真实语义验收方式
local 重启后主要是收敛中断 journal、回滚 cursor，不一定自动重新执行 engine。 首次访问后确认收敛；再由客户端显式 commit，核验消息最终落库。
cluster 通过 control store 和租约机制接管非终态 commit。 无流量等待租约过期，确认 recovery started，再轮询到最终终态。

需要改进：local 和 cluster 必须分开出报告，不能汇总成一个“重启恢复成功率”。两者的产品承诺不同。

S6：2 小时混合长跑，验证资源是否泄漏

做法：基线流量持续 2 小时，期间插入小型 commit 风暴和短暂模型抖动。

看什么：RSS 增长、线程数、文件描述符、队列深度、错误日志趋势、索引文件增长和恢复后的积压。

需要改进：“RSS 增长 < 10%”必须先定义基线时间点和允许的索引增长。建议同时报告“原始 RSS”“扣除新增 atom/索引后的 RSS”“峰值 RSS”，否则正常数据增长可能被误判为泄漏。

需要改进：2 小时只能发现一部分泄漏，不能证明没有泄漏。最好增加每 10 分钟快照，并用线性回归观察增长斜率。

四、结合前面真实模型测试的结论

已观察到的事实

  1. PR397 核心测试通过，全量测试结果为 3807 passed, 30 skipped，说明代码静态回归层面没有明显阻断。
  2. 第一次真实注入失败，根因是 EchoMem 多个 engine 使用独立的 api_key_env，测试启动只设置顶层环境变量，导致 endpoint 缺少 provider/api_base/api_key/model。
  3. 补齐环境变量后，使用 deepseek-v4-flash-0731 的 EchoMem 注入请求被 DashScope 返回 HTTP 400，明确提示该端点不支持这个模型名。
  4. 恢复为 deepseek-v4-flash 后，真实 embedding 出现 provider admission 等待超过 30 秒，触发 ProviderAdmissionTimeoutError；这说明测试环境的并发/排队参数需要先单独校准。
  5. 因此前几轮没有形成有效的 LoCoMo 81 题准确率，不能把注入不完整的轮次当作 PR397 的准确率。

对压测方案的直接影响

压测开始前必须先通过“单请求真实模型 smoke + 逐 engine 配置检查 + embedding admission 校准”。否则压测报告很可能只是在测 API key、模型路由或 provider 排队，而不是测 PR397 的并发设计。

五、建议的正式执行顺序

  1. 冻结版本：记录 PR397 commit、develop merge base、测试平台 commit、配置 SHA-256。
  2. 做预检：检查所有 engine 的 provider、api_base、api_key_env、model，并对 LLM 和 embedding 各做一次真实请求。
  3. 单请求 smoke：写入一条消息、commit、poll 到终态；再做一次 search，确认不是假健康。
  4. 低并发基线：EchoMem 内部 LLM/embedding 并发为 1，完成 S1，记录稳定结果。
  5. 逐级加压：并发逐步升高，不要直接从 1 跳到 160；每档至少持续 5 分钟。
  6. 故障注入：使用 mock 只验证可控的 500/429/挂起/恢复语义，另开真实模型容量测试。
  7. 重启测试：local、cluster 分开执行，分别按各自语义判定。
  8. 数据对账：以消息全集、cursor、atom source_turn_ids、archive 终态四者交叉核验。
  9. 报告结论：将“通过”“失败”“未执行”“已知限制”“环境错误”分开，不用一个总分掩盖某一阶段未完成。

六、最终改进清单

优先级问题修改建议
P0 没有模型/配置预检，容易把环境错误当成代码故障 增加逐 engine 配置解析、模型支持检查、真实最小请求和失败即停。
P0 SLO 的成功率、P95/P99、最终一致性口径不完全统一 所有指标定义分子、分母、时间起点、终点、是否包含重试，并同时输出原始值和重试后值。
P1 真实模型压测与 mock 故障注入没有分层 拆成“真实容量压测”和“可控故障语义压测”两份结果，禁止互相替代。
P1 local 与 cluster 恢复结论混在一起 分模式执行、分模式验收，明确 local 需要后续客户端重提的限制。
P1 只设计突发风暴，长期容量证据不足 增加阶梯负载和稳定负载，观察队列是否收敛、search 是否退化。
P2 RSS 的 10% 门槛可能误判正常索引增长 按新增 atom/索引增长校正，并输出增长斜率、峰值和回收后的 RSS。

建议的最终判定：只有在预检通过、消息注入完整、真实模型请求可追溯、S1 基线完成后，S2-S6 的结果才具备可解释性。任何阶段因为 key、模型名、网络或 provider admission 失败，都应标为“环境/依赖失败”，不能直接归因于 PR397。
