EchoMem / PR #33 / M1-M3

完整并发、公平性与边界测试方式

执行方案，非实测结果

测试分为四组：先注入并验证每个租户自己的记忆；再运行 2、16、64 并发下的三种 user/session 拓扑；随后用独立租户做公平性和 Commit 洪泛；最后单独运行超长与 API 请求体边界。性能主窗口和边界窗口绝不混合统计。

当前 seed 前置条件：seed-data-64-tenants.json 里的每项是约 0.5-0.8KiB 的 LoCoMo 对话片段，不是完整 LoCoMo session。执行器必须实际读取该文件，并且只用能由同一租户注入片段回答的问题进行 Search 预检；不能使用来源不同的 query_source 作为质量断言。

seed 文件校验

64 个 tenant_index 必须连续且唯一；每条 inject_text 非空；内容 hash 与文件一致。按发言人首次出现映射 user/assistant 角色，以多条 message 写入，而不是把整段文本塞为一条 message。

Search 预检校验

给每条注入片段生成或人工选择一个“本片段可回答”的问题和预期答案。响应必须同时满足 HTTP 200、有 recall items、预期事实命中。跨来源 query、空 expected_answer 或答案不在本片段证据中，不能成为质量分母。

3. M1：2 / 16 / 64 并发容量

目的：在相同 seed、query 池、模型与服务端配置下，找出四种 user/session 形状在 Search 和 Commit 上的容量边界。每种拓扑、每个档位分开运行：Search-only、Commit-only；可另跑混合负载，但混合结果不替代基线。

拓扑C=2C=16C=64必须证明
T1 多 user × 每 user 1 session × session 内 1 并发2 user × 1 session × 116 × 1 × 164 × 1 × 1每个 session 的业务操作最大在途为 1；上一操作完成/Commit 终态后，才发下一操作
T2 多 user × 每 user 多 session × session 内 1 并发2 user、各 2 session；只激活 2 个 session8 user × 2 session × 132 user × 2 session × 1每 session 串行；C=2 时存在 4 个 session 但最多 2 个活跃，不能伪称全部并发
T3 多 user × 每 user 1 session × session 内多并发2 user；轮转使一个 session 观察到 2 在途4 user × 1 session × 416 user × 1 session × 4记录每 session 实际 peak；C=2 必须有至少一个 session peak=2，才证明 session 内多并发

每个档位的执行顺序

  1. 预热：用通过 seed 验证的 Search query 发少量请求，不计入测量。
  2. Search-only：维持目标并发 2、16 或 64；每个完成请求立即由同一 user/session 补发，持续固定测量窗口。
  3. 停发并排空：记录所有已发、未发、429、503、超时、空召回、非空召回和实际峰值在途。
  4. Commit-only：每个逻辑操作执行 open -> add -> commit -> poll。session 内串行规则限制的是业务操作，不把轮询连接数冒充 Commit 并发。
  5. 停发并排空：直到所有 Commit 终态或达到明确排空截止；保留 pending。

Commit 的两个并发数：commit_submit_http_inflight 是提交 HTTP 的同时在途数；unfinished_commit_count 是收到 202 后尚未 completed/failed 的后台任务数。两者都必须报，后者才反映 Commit 积压。

4. M2：独立租户公平性

目的：评估不同租户是否获得接近等权的服务。这里不能用同一租户内多个 user 代替租户公平性，必须使用不同认证凭据。

并发档位推荐租户/用户形状负载每个租户输出
C=22 tenant × 1 user × 1 Search session + 1 写 session等权 Search；等权 Commit已发/到达/完成、Search P95、事实命中、202/completed/failed/pending
C=164 tenant × 4 user 或 8 tenant × 2 user每租户完全相同的 Search 到达率和 Commit 计划同左；按 tenant 分行
C=648 tenant × 8 user 或 16 tenant × 4 user同上；不让单租户独占模型池同左；保留租户级队列/拒绝原因

固定预热后，所有租户进入同一测量窗口。Commit 只以窗口内 completed/s 计算吞吐，202 不计完成；Search 使用每租户 P95 的倒数计算延迟公平性：

Jain(x) = (sum(x_i)^2) / (n * sum(x_i^2))。Commit 取 x_i = completed/s；Search 取 x_i = 1/P95_i。零完成租户仍留在分母；所有租户零完成时 Commit Jain 标记无定义，不能写为 1。

T4：多 user 间大小请求混合（公平性视角）

为什么从 M1 移到 M2：大小请求混合的本质问题是"大请求是否挤占小请求的资源"——这是公平性问题，不是容量问题。只有按 user 分组对比延迟和吞吐，才能暴露 head-of-line blocking 或队列不公平。

组Search 请求Commit 请求租户数观测
小请求组短事实问句（≤100B query）短对话 Commit（1KiB 自然语言）4P50/P95/P99、空召回数、200/429/503 每租户分行
大请求组长上下文问句（64KiB query）长对话 Commit（64KiB 自然语言）4同左；与小组对比 P95 比值
超大请求组—256KiB Commit2仅观测，单独统计，不纳入 Jain

大小请求分组后：组内计算 Jain 公平性（小请求组 4 租户、大请求组 4 租户各自算），组间对比 P95 比值。如果大请求组 P95 是小请求组的 3 倍以上，说明存在排队不公平。429/503 按组分别计数，不能把 429 全部归因于"正常容量不足"——如果只有大请求组收到 429 而小请求组没有，说明限流策略本身就可能不公平。

5. M3：Commit 洪泛下的 Search 优先级

目的：确认后台 Commit 压力存在时，已验证的交互式 Search 是否仍可用。先建立健康基线，再比较洪泛窗口；客户端延迟只能反映用户可见影响，严格优先级还需要服务端队列/调度事件。

场景SearchCommit比较方式
Baseline已验证 query，固定 C=2/16/64不发只有 baseline 健康，才可以解释后续劣化比例
Uniform flood各租户等权各租户等量持续 Commit对比 Search P95/P99、错误、事实命中、queue wait
Noisy neighbor所有租户等权 Search仅 1 个租户洪泛 Commit比较洪泛租户与旁观租户，验证隔离
Heterogeneous size短 Search 与长上下文 Search 分组1KiB、64KiB、256KiB 自然语言 Commit 分组观察不同 user 的吞吐、P95、pending 与 Jain；1MiB 留给边界组

只统计 Search 时间戳落在“至少一个 Commit 已返回 202 且尚未终态”的重叠窗口内的样本。每个场景保留 Commit 时间线、Search 时间线和 server queue wait；不能用非重叠的 503/超时推断洪泛影响。

6. 超长与 API 边界：独立运行

组别用例执行结果口径
B1 请求体矩阵message / commit / search × 0、1、1KiB、64KiB、256KiB、512KiB、1MiB × text / binary共 42 个离散协议用例；每例记录实际 wire bytes、Content-Type 和是否真正发出HTTP/传输错误、reason code、耗时、服务恢复；二进制被拒绝是有效契约结果
B2 合法超长 Commit1MiB 字符的自然语言记录分段 message 写入同一 session，再 Commit 并轮询终态；验证首/中/尾事实写入成功、202、completed/failed/pending、后续 Search 质量分别记录
B3 MCP 超长1MiB 字符 add_memory真实 MCP 调用后，使用读回接口核对字节数与 hash全文回读一致只表示保存，不证明 EchoMem Commit 抽取已完成
B4 恢复每类超长用例后复用已验证的短 Search 连续请求证明异常输入没有持续污染后续召回；记录恢复前后差异

边界不进入 M1-M3：超长请求、非法二进制、0 字节和协议拒绝单独计数。它们会改变模型 token、队列和超时分布，混进 M1/M2/M3 会使容量、公平性和优先级没有可比性。

7. 每次运行必须留下的结果

M1 容量

拓扑、目标并发、实际峰值并发、每 session peak、Search P50/P95/P99、事实命中、HTTP 分布、超时、未发、Commit 202/终态/pending、排空时间、CPU/RSS。

M2 公平性

每 tenant 的 arrival、Search P95、Search 命中、Commit completed/s、pending、Jain Commit、Jain Search，以及每租户 admission/queue/reject。

M3 优先级

Baseline 与三个洪泛场景分开保存；只比较真实重叠窗口；记录 Search 相对 baseline 的 P95/P99、错误、质量、Commit 积压和 queue wait。

原始证据

records.csv、summary.json、suite.json、execution-manifest.json、阶段 JSON 日志/Prometheus 样本、seed 映射和脱敏身份清单。

最终判定规则
  • M1：“达到 C=64”要求实际峰值达到 64，不能只看到配置为 64；并说明入口错误边界、召回质量边界和 Commit 排空边界。
  • M2：只在独立租户、等权到达、相同窗口下报告 Jain；同租户 user 公平性作为补充数据。
  • M3：baseline 若已不健康，只展示洪泛原始数据，不能声称 Commit 导致劣化或 Search 具有优先级。
  • 边界：HTTP 4xx/5xx、传输失败、超时、未发和 pending 都保留；不能删除失败样本后再计算指标。
